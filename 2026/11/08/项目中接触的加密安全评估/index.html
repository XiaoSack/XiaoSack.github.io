四、KDF 协商（非对称传密钥 + 对称加密业务）

第四种就是KDF协商；因为加密算法的逻辑，对称加密走的是异或等操作，对与长文本加解密效率较高；非对称加密走的是次方的操作，对与长文本数值加解密效率极低。所以这种加密逻辑几乎都是非对称加密用来传输密钥，对称加密用户解决其他业务的文本。但是有缺陷的就是这个非对称的公钥是硬编码在js里面或者后端会回显，我们不能解密，但是我们可以加密啊，我们可以尝试自定义 preMasterKey，然后用其非对称加密的公钥加密我们自定义的preMasterKey，发送给后端，后端用自己的非对称加密的私钥解密，然后客户端和后端分别使用 KDF 派生出相同的对称密钥。至此，此时就可以解密响应的内容了。

某银行记录 起步就是客户端发送一个随机加密的字符 然后后端响应一个公钥

总结

类型 核心缺陷 危害
硬编码密钥 / IV 密钥写死在前端 JS 中 高
明文 + sign 盐值弱、可被爆破 中高
微信 code / sessionKey sessionKey 明文下发 高
KDF 协商 未校验客户端，preMasterKey 可自定义 高
请求头 Nonce Nonce 无逻辑、仅查重 中

简单的修复建议：

  • 密钥不要硬编码在前端，使用服务端下发或密钥协商，并定期轮换；
  • 签名盐值使用足够长的高熵随机值，避免被字典或暴力破解；
  • sessionKey、openid 等敏感值不要明文返回客户端，必要时加密传输；
  • 服务端要校验客户端身份与密钥协商过程，不能无条件信任客户端提交的 preMasterKey；
  • Nonce 应具备随机性和时效性，服务端要校验时间窗与签名，不能只做查重。
